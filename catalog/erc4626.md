# Invariant catalog: ERC-4626 (tokenized vault)

Each invariant is stated as an **inequality over state**, not as prose — it is checked by the
body of an `invariant_*()` / Handler action hook, not by a comment.

## Two-target rule (false-positive control)
Every invariant runs against TWO toy vaults (purpose-built contracts, not taken from any
third-party repo):

- **(a) `NaiveVault`** — a minimal ERC-4626 with no protection. Key math (round-down `mulDiv`):
  - `convertToShares(a) = totalSupply()==0 ? a : a * totalSupply() / totalAssets()`
  - `convertToAssets(s) = totalSupply()==0 ? s : s * totalAssets() / totalSupply()`
  - `totalAssets() = asset.balanceOf(address(this))`  ← the weakness: a direct transfer (donation) grows `totalAssets` without minting shares.
  - `deposit`/`mint`/`withdraw`/`redeem` — per spec, rounding down on the depositor's shares.
- **(b) `OZVault`** — `OpenZeppelin ERC4626` (openzeppelin-contracts **v5.1.0**,
  `token/ERC20/extensions/ERC4626`), `_decimalsOffset()`. Virtual-shares offset:
  `_convertToShares`/`_convertToAssets` unconditionally add `10**_decimalsOffset()` virtual
  shares and `+1` virtual asset, so a donation is diluted across the virtual shares.
  **Reference fix: `offset=3`** — with it all cross-target invariants hold (confirmed by the
  baseline run). ⚠️ **`offset=0` is a weak fix**: it leaves residual attacker profit (~1e5 wei
  in fuzzing at large values, > SLACK) — one virtual unit is not enough. Tool conclusion:
  recommended offset ≥ 3 (matches ERC-4626 practice).

**Role semantics:**
- `D` (discriminator) — MUST fail on `NaiveVault` and hold on `OZVault`. This is the fix
  criterion: the tool re-discovers the bug and stays silent on the fixed version. **There is
  exactly one discriminator — I2** (attack profit): the OZ virtual-shares offset protects
  precisely the PROFIT of the donation attack.
- `C` (control / false-positive guard) — MUST hold on BOTH. A failure on either means a real
  accounting bug or a bad formulation (fix the formulation, not the contract). Controls:
  **I3, I5, I6**.
- `D₂` (second donation-class detector) — **I7**. Like the I2 gate, it catches value extraction
  via donation-exposure, so it fails on donation-vulnerable targets (including the bare
  `NaiveVault`) and is silent only on `OZVault(offset=3)`. Not a control (FAIL on naive is
  expected), but not the sole gate either — I2 remains the fix criterion. See Finding 2.
- `P` (mechanism probe) — shows the MECHANICS of the attack (round-to-zero, price jump). Expected
  to fire on `NaiveVault`, but MAY also fire on `OZVault` — and that is NOT a bug in the fix: the
  offset does not fix round-to-zero/price, it removes the profit (I2). So probes are asserted
  only on the naive run; on OZ their values are logged (ghost) but not asserted.

> ⚠️ Common mistake (caught in review): treating I1/I4 as discriminators. On OZ with offset=0:
> `convertToShares(a) = a·(totalSupply+1)/(totalAssets+1)`, `convertToAssets(s) = s·(totalAssets+1)/(totalSupply+1)`.
> attacker `deposit(1)` + `donate(X≥1)` + victim `deposit(1)` → victim gets `floor(2/(2+X)) = 0` shares (I1 fails on OZ too),
> and `convertToAssets` grows linearly with the donation (I4 fails on OZ too). At offset=3 — the same at a donation ~2000 wei.
> But the profit (I2) on OZ is ≤ 0, on naive > 0 — which is why the discriminator is I2 only.

## Summary table
| ID | Role | Invariant (inequality) | Catches | Naive | OZ |
|----|------|------------------------|---------|-------|----|
| **I2** | **D (gate)** | for the attacker: `assetsOut + previewRedeem(sharesHeld) ≤ assetsIn` (profit ≤ 0) | donation/inflation profit | **FAIL** | **PASS** |
| I3 | C | `Σ_h previewRedeem(balanceOf(h)) ≤ totalAssets()` | over-issuance / conservation hole | PASS | PASS |
| I5 | C | `maxWithdraw(a)` is actually withdrawable; `previewRedeem(maxRedeem(a)) ≈ maxWithdraw(a)` | max*/accounting desync | PASS | PASS |
| I6 | C | rounding direction of `preview*` per EIP-4626 (preview not in the user's favor) | rounding-direction, value leak | PASS | PASS |
| I7 | **D₂ (donation)** | round-trip: `redeem(deposit(amt))` returns `≤ amt + SLACK` | value extraction via donation-exposure | **FAIL** | **PASS** |
| I1 | P | legit `deposit(amt)` with `amt ≥ DUST` succeeding → `shares > 0` | first-depositor round-to-zero | FAIL | fires¹ |
| I4 | P | a donation into a near-empty vault does not grow `convertToAssets(1 share)` beyond factor F | price-per-share manipulation | FAIL | fires¹ |

¹ I1/I4 fire on OZ as expected (the offset removes profit, not round-to-zero/price) — this is
NOT a bug in the fix; on OZ they are not asserted, values are logged as ghost. The gate is row
**I2**.

The minimum set is I1–I4; I5–I6 are added as control invariants (EIP-4626 spec + conservation),
I7 as the second donation-class detector, which close off false positives and neighboring bug
classes. In total **7 invariants**: 1 discriminator-gate (I2), 1 second donation-class detector
(I7), 3 controls (I3/I5/I6), 2 probes (I1/I4).

## I1 — no round-to-zero on a meaningful deposit `[P — mechanism probe]`
**Statement.** For any actor `a` and a call `sh = deposit(amt, a)`, if `amt ≥ DUST` (e.g.
`DUST = 1`) and the call does NOT revert, then `sh > 0`. Equivalently:
`amt ≥ DUST ⇒ convertToShares(amt) > 0`.

**Why it matters.** This is the core of the first-depositor attack. Attacker: `deposit(1)` → 1
share; `asset.transfer(vault, X)` (donation) → `totalAssets = 1+X`, `totalSupply = 1`. A victim
`deposit(V)` with `V ≤ X` gets `V*1/(1+X) = 0` shares (round-down), the assets settle in the
vault, the attacker takes them (see I2).

**How to encode (Foundry).**
- Handler.deposit: `uint256 sh = target.deposit(amt, a);` where `amt = bound(amtSeed, DUST, 1e24)`.
  The effect is immediate, so write a ghost flag directly in the action: `if (amt >= DUST && sh == 0) roundToZeroSeen = true;`
- `invariant_noRoundToZero()`: `assertFalse(handler.roundToZeroSeen());`
- Ghost: `bool roundToZeroSeen;`

**Expectation.** `NaiveVault`: the flag is set after the donation → **fails** (asserted).
`OZVault`: the offset only makes the attack more expensive (at offset=0 round-to-zero is reached
by a donation X≥1, at offset=3 — ~2000 wei) but does NOT eliminate it → the probe fires too; on
OZ it is **not asserted**, the value is written to ghost/RESULT. This is a mechanism probe, not
the fix criterion (the criterion is I2).

## I2 — the attacker makes no net profit (profit function) `[D — the sole discriminator / gate]`
**Statement (the main economic invariant, accounting by CONSERVATION).** For the designated
`attacker`, at any moment: `wealth(attacker) ≤ fundedAttacker + SLACK`, where
`wealth = token.balanceOf(attacker) + previewRedeem(balanceOf_shares(attacker))`, and
`fundedAttacker` is EVERYTHING credited to the attacker (every token mint into their hands +
donation). I.e. `profit = wealth − fundedAttacker ≤ SLACK`.

> **SLACK — a proven floor of rounding noise (reformulation §4, not a weakening).** Rounding
> moves the share price `P = totalAssets/totalSupply` only upward; a holder receives **< P** per
> someone else's operation (the share price, not "< 1 wei"). With no yield and no manipulation
> `P ≈ 1 ⇒ < 1 wei/op ⇒ < depth wei` per run; ×4 is headroom. `SLACK = 4·depth` (=256 at
> depth=64), full derivation — §"Why SLACK = 4·depth". A strict `≤ 0` caught this dust and failed
> even on OZ (the shrinker reported dust and MASKED the attack). The proof of re-discovery is not
> the fact of failure but the MAGNITUDE of the profit: the deterministic repro gives
> `profit ≫ SLACK` on naive, `profit < 0` on OZ(offset=3).

**Why it matters.** A direct encoding of the attacker profit = (withdrawn + current redeemable
value of shares) − (deposited + donated). It can be `> 0` ONLY if part of the value flowed from
the victim (via their round-to-zero in I1). The invariant catches donation/inflation as an
economic fact, not as "a missing guard".

**How to encode (Foundry).**
- Actors: `actors[0] = attacker`, the rest are victims. The fuzzer drives victim deposits → it
  creates the attack condition.
- Ghost `uint256 fundedAttacker` — EVERYTHING credited to the attacker: in `_fund` (mint before
  deposit/mint/roundTrip) and in `donate`.
- `invariant_attackerNoProfit()`:
  `uint256 wealth = token.balanceOf(attacker) + target.previewRedeem(target.balanceOf(attacker));`
  `assertLe(wealth, handler.fundedAttacker() + SLACK);`
- Ghost `int256 maxProfitSeen` — after each action `max(wealth − fundedAttacker)` (for RESULT).
  ⚠️ The fuzz value `maxProfitSeen` is seed-dependent (a non-failing campaign may not stumble onto
  the attack) — for the NUMBER use the deterministic repro (`DonationAttack.repro.t.sol`), not the
  fuzz maximum.

> **Why conservation, not inAssets/outAssets.** The early `inAssets/outAssets` accounting (sums
> deposited/withdrawn) was DROPPED as leaky: the `roundTrip`/`mint` flows and token re-minting
> bypassed the sums and produced PHANTOM profit (on OZ the "profit" came out larger than on
> naive). The balance `wealth − fundedAttacker` catches exactly the net extraction from the
> system and is robust to any actions.

**Pitfall.** Compare in assets, not shares; `previewRedeem` rounds down (in the invariant's
favor — fine). The donation MUST be counted in `fundedAttacker`, otherwise the invariant falsely
"catches" the attacker's own donation. SLACK is mandatory — without it rounding dust masks the
attack (fails on both targets by a few wei; verified in the baseline run).

**Expectation.** `NaiveVault`: the sequence (deposit 1 → donate big → victim deposit → attacker
redeem) gives `profit ≫ SLACK` → **fails** (Foundry produces a repro). `OZVault(offset=3)`: the
donation is diluted, `profit < 0` → **holds**. `OZVault(offset=0)`: I2 still fails (weak fix, see
§finding). Re-discovery criterion — the deterministic repro: `profit(naive) ≫ SLACK`,
`profit(offset=3) < 0`.

## I3 — conservation: total redeemable ≤ totalAssets `[C]`
**Statement.** `Σ_{h ∈ holders} previewRedeem(balanceOf(h)) ≤ totalAssets()`.

**Why it matters.** A solvency invariant: you cannot promise holders more assets than exist. It
catches over-issuance, double counting, errors in `_convertToAssets`. It is NOT sensitive to the
donation attack (the vault stays solvent — fairness suffers, not conservation), so it is a
**control**: holds on both. A failure = a real accounting bug.

**How to encode (Foundry).**
- The Handler keeps `address[] holders` (push on the first non-zero share balance).
- `invariant_solvency()`: loop `sum += target.previewRedeem(target.balanceOf(holders[i]));` then
  `assertLe(sum, target.totalAssets());`

**Expectation.** Holds on both (`previewRedeem` round-down guarantees `≤`). If it failed on
`OZVault` — fix the formulation (probably forgot round-down or virtual shares).

## I4 — share price cannot be inflated by a donation into a near-empty vault `[P — mechanism probe]`
**Statement.** Let `donate(X)` be a direct `asset.transfer(target, X)` by an actor that did not
`deposit`. If before the donation `totalSupply() ≤ SMALL` (e.g. `SMALL = 1e3`), then
`convertToAssets(ONE) * DEN ≤ convertToAssets_before(ONE) * (DEN + F*DEN)` — i.e. the share price
(`convertToAssets(ONE)`, `ONE = 10**decimals`) does not jump by more than `(1+F)` from one
donation. By default `F = 1` (no more than ×2).

**Why it matters.** This is the attack mechanism at the price level: on a naive vault
`convertToAssets` grows linearly with the donation at tiny `totalSupply`, which zeroes out the
victim's shares. The invariant records the price jump itself, complementing I1/I2 at the
mechanics level (useful for explaining the repro).

**How to encode (Foundry).**
- In Handler.donate, before the transfer: `uint256 before = target.convertToAssets(ONE);` after:
  `uint256 aft = target.convertToAssets(ONE);`
  `if (target.totalSupply() <= SMALL && aft > before * (1 + F)) priceJumpSeen = true;`
  (read `totalSupply` BEFORE the transfer for the near-empty condition).
- `invariant_noDonationPriceJump()`: `assertFalse(handler.priceJumpSeen());`

**Pitfall.** Initial `totalSupply()==0`: `convertToAssets` may be degenerate — take `before` when
`totalSupply>0`, otherwise skip the action. Tune the threshold `F` so that `OZVault` with offset=0
passes (its jump is limited by the virtual 1 asset + offset).

**Expectation.** `NaiveVault`: the price jump from a donation is unbounded → **fails** (asserted).
`OZVault`: the virtual `+1` in the `convertToAssets` denominator slows but does not bound the
growth (the numerator `totalAssets+1` grows linearly with the donation) → the probe fires too; on
OZ it is **not asserted** (ghost/RESULT). A mechanism probe, not the fix criterion (criterion —
I2).

## I5 — maxWithdraw / maxRedeem consistency `[C]`
**Statement.** For any holder `a`:
(1) **[always]** `withdraw(maxWithdraw(a), a, a)` does NOT revert (the max is actually withdrawable);
(2) **[CONDITIONAL]** `previewRedeem(maxRedeem(a)) == maxWithdraw(a)` (with rounding tolerance `±1 wei`).

> Part (2) is **conditional**: on vaults with a withdrawal fee, with async/queued withdrawal
> (ERC-7540), with limits/pauses — **enable it** (it catches the desync when maxRedeem and
> maxWithdraw diverge beyond rounding). On a fee-free vault (including both of our demo targets)
> it degenerates into a tautology, so **in the demo harness it is NOT asserted** (see below). The
> catalog is a reusable spec for the whole protocol type, not only for the current demo, so part
> (2) stays in the spec.

**Why it matters.** A desync of `max*`/`preview*`/actual withdrawal = either stuck funds (a DoS on
withdrawal) or a withdrawal beyond one's share. A control: per EIP-4626 it must hold on a correct
implementation.

**How to encode (Foundry).**
- Part (1), asserted in the demo: Handler.withdrawMax: `uint256 mw = target.maxWithdraw(a); vm.prank(a); try target.withdraw(mw, a, a) {} catch { maxWithdrawReverted = true; }`;
  `invariant_maxWithdrawHonored()`: `assertFalse(handler.maxWithdrawReverted());`
- Part (1b), redeem branch: Handler.redeemMax: `uint256 mr = target.maxRedeem(a); try target.redeem(mr,a,a) {} catch { maxRedeemReverted = true; }`;
  `invariant_I5b_maxRedeemHonored(): assertFalse(handler.maxRedeemReverted());` — a strengthening (not a weakening) of the shared code.
- Part (2), only for vaults with a fee/queue (NOT enabled in the demo harness):
  `invariant_maxConsistency()`: for each holder `assertApproxEqAbs(target.previewRedeem(target.maxRedeem(a)), target.maxWithdraw(a), 1);`

**Expectation.** Part (1) holds on both (asserted). Part (2) — a tautology on fee-free targets
(not asserted); on a vault with a fee/queue a failure = a real desync bug (or too tight a
tolerance — then fix the tolerance).
**3 mechanisms of the I5 class:** `BugMaxWithdrawVault` (I5, withdraw per-tx cap),
`BugMaxRedeemLiesVault` (I5b, maxRedeem inflated), `BugRedeemCapVault` (I5b, redeem per-tx cap).
All FAIL on their own, OZ(3) HOLD. See §"Validation matrix".

## I6 — rounding direction of preview* per EIP-4626 `[C]`
**Statement.** Preview functions must NOT round in the user's favor (otherwise — value leaks out
of the vault). Per spec:
- `previewDeposit(a) ≤ actualShares(deposit(a))` (preview does not overstate shares issued),
- `previewMint(s) ≥ actualAssets(mint(s))` (preview does not understate assets required),
- `previewWithdraw(a) ≥ actualShares(withdraw(a))` (preview does not understate shares burned),
- `previewRedeem(s) ≤ actualAssets(redeem(s))` (preview does not overstate assets returned).

**Why it matters.** A wrong rounding direction = systematic free value for a user at everyone
else's expense. A control: must hold on both.

**How to encode (Foundry).** In the corresponding action hooks, compare the preview (taken BEFORE
the operation) with the operation's actual return; on a violation set a ghost flag, check
`assertFalse(...)` in separate invariants.

**Expectation.** Holds on both. A failure = a real rounding-direction bug.

## I7 — round-trip with no profit `[D₂ — second donation-class detector]`
**Statement.** For any actor: `redeem(deposit(amt, a), a, a) ≤ amt + SLACK` — an immediate
deposit→redeem does not return more than was deposited beyond rounding dust (no "free" mint on
rounding). The same tolerance as in I2 (round-down compounds to a few wei). Ghost
`maxRoundTripOvershoot` = max `(back − amt)` — measured in the baseline (dust).

**Why it matters.** If a round-trip gives `> amt`, the attacker milks the vault in cycles. A
correct vault rounds in its own favor on both ends (`≤ amt`); a donation-exposed vault lets the
first depositor absorb the donation → overshoot.

**How to encode (Foundry).** Handler.roundTrip: `uint256 sh = target.deposit(amt,a); uint256 back = target.redeem(sh,a,a);
if (back > amt) maxRoundTripOvershoot = max(maxRoundTripOvershoot, back - amt);` +
`invariant_noRoundTripProfit(): assertLe(maxRoundTripOvershoot, SLACK);`.

**Expectation.** Fails on donation-exposed targets (including the bare `NaiveVault`: `donate` into
an empty vault → the first depositor absorbs the donation, overshoot = donation ≫ SLACK). Silent
**only on `OZVault(offset=3)`** (overshoot is dust ≤ SLACK). I7 is not a control but the second
donation-class detector (alongside I2); the false-positive controls are I3/I5/I6.

## Why SLACK = 4·depth
SLACK is not a fudge but a proven ceiling on rounding noise.
- Rounding in ERC-4626 always moves the share price `P = totalAssets/totalSupply` only **upward**:
  shares on the way in (`deposit`/`mint`) round floor (in the vault's favor), assets on the way
  out (`withdraw`/`redeem`) round ceil on shares. Provable for all 4 operations ⇒ a holder does
  NOT lose on others' operations but gains a small remainder.
- Per someone else's operation a holder receives **< P** (not "< 1 wei", but less than the share
  PRICE): a remainder < 1 share is dropped.
- No yield ⇒ without manipulation `P ≈ 1` ⇒ dust **< 1 wei/op** ⇒ **< depth wei** per run. The
  factor **×4** is headroom for several rounding points in one sequence. Hence `SLACK = 4·depth`.
- **Yield vault:** ceiling = `depth·P_benign` (P under normal operation) — recompute for the
  specific vault.
- **Heavy run:** `SLACK = 4·depth` under the NEW depth (grows linearly with the sequence length).
Empirics (baseline 256/64, depth=64 ⇒ SLACK=256): offset=3 holds (dust ≤ SLACK), naive profit ≫
SLACK, offset=0 > SLACK.

### Finding: a price-aware threshold was considered and REJECTED (it masks the gate)
A clean run with no replay cache revealed: the absolute `SLACK=256` on RARE seeds gives marginal
dust breaches of I2 on SOME bug targets (BugMaxWithdraw +1373w, BugRounding +~2e9w — benign dust
at amounts up to 1e24). We considered a price-aware `SLACK_assets = 4·depth·P` (P = max
`convertToAssets(1 wei of shares)` over the run). EMPIRICALLY REJECTED: it **kills the I2 gate** —
under donation inflation the share price P soars to ~(D+V), the attack profit = V < P, so
`4·depth·P ≫ V` and I2 PASS on NaiveVault/BugMinDeposit (the gate is dead). Reason: the
donation-attack profit scales ∝ P just like the dust, they cannot be separated by a P-scaled
threshold. **Decision (methodology):** keep the ABSOLUTE `SLACK=256` (the gate stays alive), and
reformulate the "zero false positives" criterion by TARGET, not by magnitude: a false positive =
a failure on a CORRECT target (OZ offset=3) or on a SOUND control's own role; a BUG target MAY
drop several invariants (bonus detection, not a false positive). Pinning `FOUNDRY_FUZZ_SEED` — for
reproducibility of the RESULT numbers; correctness (OZ3 holds everything) was checked on 2–3
seeds. The ghost `maxSharePrice` is kept in the Handler for the RESULT number P (not in the
threshold). A valuable methodological result: price-aware looks "more honest" but is structurally
blind to the donation class.

## Finding: `offset=0` is a weak fix (offset ≥ 3 required)
The tool showed that `_decimalsOffset()=0` is NOT a sufficient protection:
- **I2 fuzzing:** on `OZVault(offset=0)` I2 **fails** (the attacker extracts profit > SLACK on
  complex multi-operation sequences) — one virtual unit (`+1` asset / `10^0=1` share) is not
  enough at large values.
- **Deterministic repro (a simple canonical scenario):** at offset=0 the attacker is no longer in
  profit (−3.33e20), BUT **the victim still loses ~33%** of the deposit — the value gets stuck in
  the virtual shares, the attack is destructive even though it does not enrich the attacker. At
  `offset=3` the victim loss drops to ~0.025% (dust).
- **Conclusion:** recommended `offset ≥ 3`. Matches ERC-4626 practice (OpenZeppelin ERC4626 docs;
  Euler "Exchange Rate Manipulation in ERC4626"). `offset=3` is the main control target; `offset=0`
  is kept in the tests as a demonstration of a weak fix.

## Catalog validation: known bugs
To show that the tool catches not a single bug (I2/donation) but that EACH invariant catches its
own class and stays SILENT on a correct contract, toy vulnerable targets were added (purpose-built,
not from any third-party repo) — one per known bug class. The "tool is silent" control is
`OZVault(offset=3)` (all I2–I7 PASS).

**Matrix "invariant → bug class → where it fails / where it is silent" (baseline 256/64, SLACK=256):**

| Inv. | Bug class | Fails on (vulnerable) | Silent on (control) |
|------|-----------|-----------------------|---------------------|
| I1 | round-to-zero (probe) | NaiveVault (deposit→0 shares after a donation) | OZ(3) |
| **I2** (gate) | attacker profit (donation inflation) | NaiveVault (no protection) **+** BugMinDepositVault (protection theater) **+** OZ(offset=0) (weak fix) | **OZ(offset=3)** **+** BugDeadSharesVault (sound dead-shares) |
| **I3** | over-issuance / insolvency | BugSolvencyVault (unbacked issuance) | Naive, OZ(3) |
| I4 | price-jump (probe) | NaiveVault (share price jump from a donation) | OZ(3) |
| **I5** | max* desync / withdrawal DoS | BugMaxWithdrawVault (per-tx cap under maxWithdraw) | Naive, OZ(3) |
| **I6** | rounding-direction (rounding in the user's favor) | BugRoundingVault (direction probe) | Naive, OZ(3) |
| I7 | round-trip profit | donation family (Naive, BugRounding, BugMaxWithdraw, BugMinDeposit) + BugRounding | **only OZ(3)** |

**I2 is confirmed on TWO different vulnerable contracts** (NaiveVault donation + BugMinDepositVault
"protection theater") and is SILENT on TWO different correct ones (OZ offset=3 + dead-shares) — an
assurance that the gate catches the CLASS "attacker profit", not a specific implementation.

**Vulnerable targets (`src/Bug*Vault.sol`) and deterministic repros (`test/ValidationRepros.repro.t.sol`):**
- `BugRoundingVault` — all rounding flipped in the user's favor (Ceil on in/out). Intended **I6**.
  Repro: `deposit(1000)→redeem` at price 1.5 returns **1001 > 1000**; on OZ(3) — 999 ≤ 1000.
- `BugSolvencyVault` — fixed 1:1 price + issuance of `assets+1` shares (unbacked). Intended **I3**.
  Repro: after `deposit(1000)` the sum redeemable is **1001 > 1000** totalAssets; on naive — 1000 = 1000.
- `BugMaxWithdrawVault` — honest `maxWithdraw`, but a per-tx `WITHDRAW_CAP` on withdrawal. Intended **I5**.
  Repro: `withdraw(maxWithdraw=2e21)` at cap=1e21 **reverts**; on naive — passes.
- `BugMinDepositVault` — a min-deposit "protection", share math untouched. Second failing **I2**.
  Repro: donation attack profit **+1e6 > SLACK**; on OZ(3) — −1e18 (attacker loss).
- `BugDeadSharesVault` — fixed dead shares 1e3 (Uniswap V2 style). **I2 is SILENT** (sound protection — see below).

### Finding 1: fixed dead-shares is a SOUND protection against the basic donation attack (not a "weak fix")
Contrary to the initial expectation (dead-shares as a weak protection), fixed "dead" shares `m`
PROVABLY prevent single-victim donation inflation. The attacker profit at deposit `D`, donation
`B`, victim deposit `V`: `profit = (V·D − m·(D+B)) / (D+m)`. Profit > 0 requires `V·D > m·(D+B)`,
but the victim rounding to zero requires `V < price ≈ (D+B)/D`; at `m ≥ 1` these conditions are
incompatible ⇒ `profit ≤ 0`. Empirics: I2 **PASS** on `BugDeadSharesVault`; repro — profit
**−9.99e20** (attacker at a loss), while THE SAME attack on `NaiveVault` gives **+1e21**. So
dead-shares(1e3) in the matrix is the SECOND I2 CONTROL (an example of a sound protection
different from OZ virtual-shares), not a buggy target. (The practical move of protocols to
virtual-shares is motivated not by this attack but by the loss of real capital to dead shares,
griefing, and multi-step scenarios — outside this demo.)

### Finding 2: I7 is donation-sensitive, not a pure per-bug discriminator
I7 (round-trip overshoot > SLACK) fails across the whole family with donation-exposure (including
the bare NaiveVault: `donate` into an empty vault → the first depositor absorbs the donation,
overshoot = donation). That is, I7 catches the same donation class as I2 and is NOT a pure control
on naive. The only target where I7 is silent is `OZVault(offset=3)`. Reclassified I7 from `C`
(control) to `D₂` (second donation-class detector), and the round-trip is NOT complicated with
donation accounting (simpler and more honest). This removes the mismatch between the original
wording ("I7 holds on both") and the RESULT table where `Naive I7 = FAIL`. The false-positive

## Validation matrix: ≥3 mechanisms per invariant
Deepening the validation to ~3 DIFFERENT mechanisms per invariant — to prove that the invariant
catches a CLASS. Honesty discipline: where there is honestly no 3rd/2nd mechanism — a note, not
fabrication (precedent: dead-shares above). **Zero-false-positive criterion:** the UNIVERSAL
correct target = ONLY `OZVault(offset=3)` — holds ALL I1–I7 on 2–3 seeds. A bug target MAY drop
several invariants (bonus detection, intended one in **bold**). `BugDeadShares` is the SOUND
control FOR I2 (its I7 FAIL is correct per Finding 2, not a false positive). Harness: `NaiveVault`
→ virtual (refactor without behavior change) for the override targets;
`+invariant_I5b_maxRedeemHonored` (I5 redeem branch, a strengthening, shared code not weakened);
ghost `maxSharePrice` (RESULT number P).
